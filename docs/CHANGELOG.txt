Initial build and first several rounds of iteration, across multiple
sessions in the same working day. This repo began as a repurposed
DickoClicko checkout; per explicit user decision (asked via AskUserQuestion
rather than assumed) the public GitHub history was started fresh -- a

in that commit alone -- the cumulative diff since the fresh initial commit
d1d3c96).

A concurrent Claude session built the ball-physics/hand-collision system
(gravity, wall bounce, 3-capsule finger collision against a per-frame-
annotated skeleton) and the skeleton-annotation tool
(scripts/active/flick-skeleton-annotator.html) in parallel with the work
described below -- their own session isn't represented in this entry's
own Added/Fixed/Verified detail, only reviewed and built on top of.

Added:
- Mouse-follow hand entity that continuously rotates to point its pre-drawn
  "up" orientation at the viewport's centerpoint, switching between 8
  directional animation sets (Behind, Behind Thumb, Side Thumb, Front
  Thumb, Front, Front Pinky, Side Pinky, Behind Pinky) based on the mouse's
  angle from center, in exact 45-degree sectors per the user's own spec.
- Click-to-play forward+reverse flick animation per direction, with a
  dev-tunable "Peak Frame Hold" (0-10 extra frames at the fully-extended
  pose before reversing).
- A §12-compliant dev panel, built from the workspace's own
  TEMPLATE_DEV_PANEL.html, with Entity/Background/Debug groups (settings
  decomposed per CLAUDE.md §12n).
- Per-direction Hand Rotation Offset: a dropdown + slider compound row (8
  independently-persisted values, not forgotten when switching the
  dropdown without saving) replacing an earlier single global offset.
- Top-edge ball collision, except during the ball's initial fall into frame
  from its off-screen-above spawn point (a deliberate exception so it isn't
  immediately bounced back out before ever being seen).
- A ball-proximity auto-trigger for the flick sequence: the sequence starts
  automatically (no click needed) when the ball enters the union of the
  hand's own collision capsules across every frame of the animation
  sequence, not just one pose -- per explicit correction from an initial,
  narrower "peak frame only" spec.
- Converted the physics loop from a raw per-real-frame delta to a fixed
  1/60s timestep accumulator, for reproducible ball motion given identical
  inputs (a static mouse position included).

Fixed:
- mouseX/mouseY/entityX/entityY could read/derive from
  window.innerWidth/innerHeight at 0 (a real early-page-life quirk,
  reproduced in this session's own testing, same class already documented
  elsewhere in this workspace for mobile Safari/Chrome) -- permanently
  stranding the entity off-screen. Fixed by deferring the real center-based
  initialization into the physics loop's own first live tick.
- The canvas element itself could get stuck at 0x0 CSS size from the same
  root cause, with no later correction -- besides breaking rendering/hit-
  testing, this is the likely cause of a real "Hide OS Cursor doesn't work"
  report, since a 0x0 element has no real screen area for `cursor:none` to
  apply to. Fixed with a per-frame self-healing size check.
- 2 stale dev-panel groups ("Hand Animation", "Mouse / Rotation" -- both
  renamed/consolidated away from mid-session) kept reappearing as empty
  ghost groups for anyone whose browser had already saved dev-panel
  settings referencing those names, since the generic panel engine
  correctly (by design) recreates any saved group it doesn't recognize as
  a real user-created one. Fixed with a small, one-time-per-load migration
  that moves their rows into Entity and removes the empty shell.

Verified:
- Entity rotation math against 2 independent geometric cases (mouse
  directly above / directly right of center) before trusting it.
- The per-direction rotation-offset persistence (switch away, switch back,
  Save, Reset, and a full page reload) via real event dispatches against
  the live DOM, not just code review.
- The ball-proximity auto-trigger via 4 separate live tests driving the
  real production functions with controlled inputs, including a case that
  only the corrected "any point in the sequence" (not "peak frame only")
  design could pass.
- The fixed-timestep determinism claim rigorously: 2 differently-jittered
  synthetic real-frame-timing sequences, compared at matching TOTAL FIXED-
  STEP COUNT (not wall-clock callback index), produced bit-for-bit
  identical ball position across all 192 directly-comparable steps.

2026-09-10 (continued) -- spawn-placement-mode branch, uncommitted

A major architecture rework, proposed and explicitly approved by the user
before implementation (CLAUDE.md §0a) on a new `spawn-placement-mode`
branch, plus several follow-on refinement rounds in the same session.

Added:
- Spawn-and-place model, replacing the mouse-anchored entity entirely: the
  animation is invisible on load; a 2-click gesture (1st click = fixed
  anchor point, 2nd click = aim point) spawns a new, independently-tracked
  entity along that line, at whichever of the 8 directions the line's angle
  falls into. Multiple entities can be placed at any angle; each keeps its
  own play/collision/trigger state. Manual click-to-flick was retired
  (every click is now part of the spawn/adjust gesture) -- the ball-
  proximity auto-trigger, generalized to loop over every entity
  independently, is the only way any entity's flick fires.
- Entity anchor point changed from image centroid to the bottom-center of
  the frame's actual VISIBLE (non-transparent) content -- a one-time-per-
  direction alpha-channel scan (computeVisibleContentBounds), cached per
  direction. Confirmed real, non-trivial padding in the raw PNGs (e.g.
  'front': centerX=0.4765, bottomY=0.9145, not the naive 0.5/1.0).
- Swept (segment-vs-segment closest-approach) ball-vs-finger collision,
  replacing a point-only test -- fixes a fast ball tunneling clean through
  the hand between 2 physics ticks without ever registering a hit.
- Live drag preview: while aiming (between the 1st and 2nd click), the
  actual sprite renders translucently at the real live angle/direction, so
  the user sees exactly what will be placed before committing.
- Start/Stop buttons (always-visible UI, independent of the dev panel):
  Start lets balls spawn and fall; Stop halts spawning and clears any ball
  on screen immediately. Entity placement is gated to Stop mode only.
- Stop-mode entity adjustment: 2 draggable dots per entity (base = the
  fixed anchor point, end = the original aim point) plus a dashed
  connecting line. Dragging the base dot translates the whole entity
  (moves, keeps its rotation); dragging the end dot keeps the base fixed
  and rotates the entity in place, recomputing direction/rotation with the
  same formula the original 2-click spawn gesture uses (switching
  direction, and preloading its frames, if the drag crosses a 45-degree
  sector boundary).

Fixed:
- A freeze-on-first-click regression that the visible-content anchor scan
  itself introduced: computeVisibleContentBounds ran at full image
  resolution (measured 36-83ms per direction), and the new live drag
  preview called it every animation frame for whichever direction the
  mouse currently pointed toward -- sweeping across multiple direction
  sectors while aiming chained several of these expensive scans together,
  reading as a hang. Fixed by scanning a downscaled (200px) copy of the
  image instead of the original (measured: sub-1ms per direction after a
  one-time ~30-56ms warmup on the very first scan).

Verified:
- The spawn-placement rework end-to-end via real synthetic click sequences:
  correct direction bucket/rotation for 2 different line angles, entities
  staying fixed and independent of later mouse movement and of each other,
  per-entity trigger isolation (forcing the ball onto one entity's tip only
  flipped that entity's own playing flag), and that clicking an already-
  spawned entity does NOT trigger it (starts a new spawn pair instead).
- Both anchor-point changes visually (screenshot comparison, and a
  temporary debug-marker crosshair at the entity's own exact anchor point)
  and via the joint-collision debug lines, confirming the collision
  geometry stayed in sync with the sprite draw through both changes.
- The swept-collision algorithm in isolation (a fast ball crossing a
  segment mid-tick correctly resolved at the true crossing point, where
  the old point-only test would have missed it by 30px), then via a
  realistic end-to-end integration test (a 500px/tick ball correctly
  caught and resolved; the collision velocity kick still applies correctly
  using real per-tick joint-speed data).
- The live drag preview matches exactly what gets committed on the actual
  2nd click (same direction, same rotation, to 2 decimal places).
- The freeze fix via direct timing measurement (before/after) AND a full
  realistic interactive end-to-end test matching the user's own reported
  flow (click, sweep the mouse across 5 direction sectors via hover,
  confirm `document.readyState` stays "complete" throughout with no hang,
  2nd click completes the spawn correctly).
- Start/Stop and the draggable dots live: base-dot drag confirmed to
  translate x/y AND the end point by an identical delta with rotation/
  direction unchanged; end-dot drag confirmed to leave x/y fixed while
  rotation changed (screenshot-confirmed the hand visibly rotating in
  place); Start confirmed to hide the dots, disable itself, and spawn a
  falling ball; Stop confirmed to clear the ball immediately and re-show

Fixed:
- The dev panel (#devPanel) had no default-hidden state -- only a runtime
  toggle. On any genuinely fresh page load (no saved localStorage, which
  describes a real first-time visitor), the panel rendered wide open,
  covering most of the left/upper viewport including the Start/Stop
  buttons. A click meant to place an entity's first anchor point landed on
  the panel instead of the canvas -- nothing happened, indistinguishable
  from a freeze to a user with no reason to suspect an invisible overlay
  was eating their clicks. This session's own earlier verification never
  caught it because it reused an already-open browser tab where the panel
  had already been manually hidden once, and that hidden state persisted
  in the live DOM across reloads (not via localStorage) -- masking the
  bug for every test after the first. Fixed by adding the `hidden` class
  to `#devPanel` directly in the static HTML so it now boots hidden by
  default; the existing "DEV" corner button still opens it on demand.
- Added defensive try/catch around the visible-content anchor scan
  (computeVisibleContentBounds, inside visibleBoundsForDirection) as a
  precaution -- render() has no try/catch above it in the call stack, so
  any uncaught throw there (e.g. a possible canvas-taint SecurityError on
  some browsers for a file://-opened page) would silently kill the whole
  animation loop after the first placement, looking identical to a real
  freeze. Falls back to, and caches, the same existing 0.5/1 default on
  any throw. Not confirmed as the actual cause of this particular report
  (the dev-panel default explains it fully on its own) -- added as
  hardening, labeled honestly as such.

Verified:
- Reproduced against a genuinely fresh load (`localStorage.clear()` +
  reload, not the already-configured tab used for every earlier test) --
  confirmed via screenshot the panel now starts hidden with the canvas
  fully clickable, then confirmed a real 2-click placement sequence spawns
  an entity correctly with no freeze (`document.readyState` stayed
  "complete" throughout).

2026-09-10 (continued yet again) -- mobile performance: DPR cap + pre-scaled
idle-sprite cache

"i tested the app out on mobile and the placing, rotating, moving of the
entities are very very laggy." No mobile hardware available to profile
directly -- addressed with 2 well-established canvas performance
practices rather than a single confirmed root cause.

Fixed:
- The canvas's own backing store was sized off the RAW
  `window.devicePixelRatio` -- many phones report 3 or higher, making the
  actual pixel buffer up to 9x larger than DPR 1 for the identical
  on-screen CSS size (3x width * 3x height), with every fillRect/drawImage
  this file does filling into that full buffer. Added `effectiveDpr()`
  (caps at 2) and routed BOTH `resizeCanvas()` and `update()`'s own
  self-healing size-mismatch check through it (they must agree, or the
  mismatch check would call `resizeCanvas()` -- a full backing-store
  reallocation -- every single frame).
- Every idle (non-playing) entity, AND the live spawn/drag preview, drew
  from the full-resolution source image (up to 2400x1181px per frame)
  every single frame, letting the browser rescale it down to on-screen
  size on every call -- exactly the 2 draw paths active while placing,

2026-09-11 -- fix: click-and-drag entity placement broken on mobile
touchscreens

"clicking and dragging to place entities doesnt work on mobile. check
some touch screen thing, or maybe its some chrome browser on touchscreen
thing"

Root cause: `#scene` (the canvas) had no `touch-action: none` -- every
other draggable element in this file (`.dev-header`, the dev-panel
resize edges/corners) already sets it, the canvas never did. Without it,
a real touchscreen's native gesture recognizer treats a press-drag on
the canvas as a pan/scroll attempt and hijacks the touch mid-gesture,
firing `pointercancel` instead of letting `pointermove`/`pointerup`
continue -- kills exactly the press-drag-release placement gesture while
a plain tap (not enough movement to trigger the browser's own pan
detection) keeps working, matching the report precisely.

Fixed:
- Added `touch-action: none` to `#scene`'s CSS rule.
- Added a `window` `pointercancel` handler (mirroring the existing
  `pointerup` handler's own cleanup) that clears
  `draggingEntity`/`draggingPoint`, and -- when the cancelled pointer
  matches `spawnPointerId` -- `pendingSpawnStart`/`spawnPointerId` too.
  Not part of the reported bug itself, but directly relevant to making
  the fix robust: without it, a genuine cancel that `touch-action: none`
  doesn't prevent (an OS interruption, an edge-swipe navigation gesture)
  would leave `pendingSpawnStart` stuck, silently blocking every future
  placement until an unrelated tap happened to land far enough away to
  complete the stale gesture.

Verified:
- `getComputedStyle(#scene).touchAction` confirmed `"none"` live in the
  browser tool's own mobile-viewport emulation (375x812).
- A full press-drag-release gesture dispatched as synthetic touch-type
  `PointerEvent`s (`pointerdown` -> `pointermove` x2 -> `pointerup`, 100px
  of movement) on the canvas completed end-to-end: `spawnEntityFromLine`
  fired, entity count went 0 -> 1, screenshot-confirmed the new entity
  rendered at the drag's end point.
- Syntax-checked all inline `<script>` blocks after both edits.

Explicit, disclosed limitation: a JS-dispatched `PointerEvent` never
goes through a real browser's native touch-gesture recognizer, so this
environment cannot reproduce the actual hijack-and-cancel failure mode
itself -- only code inspection (matching the same `touch-action: none`
convention already used by every other draggable element in this exact
file) identifies the root cause and fix with confidence. The user should
re-test on their actual phone to confirm the real-hardware fix.
